Model how your team really works: named roles, reviews that send work back, and a record in plain files.

You describe how work should move from a request to a checked result: the
steps, who does each one, the reviews, and where a person decides. Obversa
runs that workflow one bounded engine call at a time.

Agents aren't deterministic, so nothing guarantees that every step of a
process is followed, in the right order, under the right conditions.
Obversa puts a deterministic process around the inference: many small jobs,
each with a review cycle. A workflow built into a frontier harness can't be
saved, shared or repeated. An Obversa workflow is a file you save, share and
run again. It models process at every layer: the organisation, the team and
the individual.

## Inference at the leaves

Inference belongs mostly at the leaves. Around each inference step you can
build as much process as you like: deterministic scripts, tools and checks,
so the job an agent has to do is clearer, simpler, better bounded and
cheaper. Squeeze the determinism out of the agents and what's left is a set
of very specific, focused agents doing narrow tasks.

That improves quality. It also means a small open-weight model tuned to a
narrow, well-bounded task can do it as well as a frontier model would, at a
fraction of the cost. [What Obversa is](/concepts) explains the method.

## See a team run

The file below has nine named stages, the way a real team delivers a
feature. A Claude seat
writes the context, the requirements and the plan, and a reviewer accepts
each one before the next begins. A Codex seat writes the tests before any
code exists, and a reviewer reads them. The same seat then implements until
the tests pass and the review panel accepts. A person decides whether to
ship, and the last stage writes up the evidence. A red test or a rejected
review sends the work back to the stage that owns it, with the findings.
The file is complete. Write your brief to `briefs/triple.md` and run it.

```ts
import { claude } from '@obversa/engine-claude-cli';
import { codex } from '@obversa/engine-codex-cli';
import { run } from '@obversa/runtime';
import { briefFromFile, person, stage, workflow, type TeamSeat } from '@obversa/runtime';

interface FeatureDeliveryEngines {
  readonly claude: (model: string) => TeamSeat;
  readonly codex: (model: string) => TeamSeat;
}

const realEngines: FeatureDeliveryEngines = { claude, codex };

/**
 * A feature, delivered the way a team delivers one. The roles are named once;
 * every stage is a small block of nouns: who does it, what it writes, who
 * reads it, where a red result goes back to. Inference happens only where a
 * role is named; every other stage is a command or a person.
 */
function createFeatureDelivery(engines: FeatureDeliveryEngines = realEngines) {
  return workflow('feature-delivery', {
    brief: briefFromFile('briefs/triple.md'),
    options: { timeout: '10m' },

    roles: {
      analyse: engines.claude('claude-sonnet-4-5'),
      implement: engines.codex('gpt-5.6-luna'),
      'research-review': [engines.codex('gpt-5.6-luna')],
      'code-review': [engines.claude('claude-sonnet-4-5')],
      approve: person('Ship this change?'),
    },

    stages: [
      stage('research-context', {
        agent: 'analyse',
        writes: 'team-output/research-context.md',
        desc: 'Read the workspace and write down what the change touches.',
        gate: 'The context note is in the workspace and a reviewer has accepted it.',
        reviewedBy: 'research-review',
        retry: 3,
      }),

      stage('research-requirements', {
        agent: 'analyse',
        writes: 'team-output/research-requirements.md',
        desc: 'Turn the brief and the context note into requirements, one REQ-n per line.',
        gate: 'The requirements note is in the workspace and a reviewer has accepted it.',
        reviewedBy: 'research-review',
        retry: 3,
      }),

      stage('plan', {
        agent: 'analyse',
        writes: 'team-output/plan.md',
        desc: 'Write an executable plan from the requirements, one check per REQ-n.',
        gate: 'Every requirement has a check in the plan.',
        reviewedBy: 'research-review',
        retry: 3,
      }),

      stage('tests-first', {
        agent: 'implement',
        writes: 'test/triple.test.mjs',
        desc: 'Write the declared test files from the accepted plan before any implementation exists.',
        gate: 'Every declared test file exists and covers the plan.',
        reviewedBy: 'code-review',
        retry: 3,
      }),

      stage('implement', {
        agent: 'implement',
        writes: 'src/triple.mjs',
        desc: 'Write the code to the plan and the tests.',
        gate: 'The source file exists.',
        retry: 3,
      }),

      stage('test', {
        run: ['node', '--test', 'test/triple.test.mjs'],
        desc: 'Run the tests; a red run goes back to implement with the output.',
        gate: 'The test command exits 0.',
        sendsBackTo: 'implement',
      }),

      stage('review', {
        panel: 'code-review',
        agree: 1,
        desc: 'Read the change and the test result against the plan.',
        gate: 'At least one reviewer has accepted the change.',
        sendsBackTo: 'implement',
      }),

      stage('approve', {
        input: 'approve',
        desc: 'Put the verified change in front of a person.',
        gate: 'A person has said yes.',
      }),

      stage('close', {
        agent: 'analyse',
        writes: ['team-output/evidence.md', 'team-output/learning.md'],
        desc: 'Write the evidence of the run and what was learned, from the record alone.',
        gate: 'Both notes are in the workspace.',
      }),
    ],
  });
}

const result = await run(createFeatureDelivery());
console.log(JSON.stringify(result.outcome, null, 2));
```

<Warning>
Run the file in a directory you're happy for a model to change. The Claude
seat runs with permission prompts off, so it can write anywhere the process
can.
</Warning>

Write many small jobs, each with its own review, for the specific research,
implementation and test tasks in your process, rather than a few large
ones. A coarse step hands the whole task to one inference and hopes. A
small step with a review cycle is a process the run can hold to. Treat the
team above as a starting point, and add steps as your process needs them.

A real run of this file stopped at the question for the person:

```json
{
  "status": "paused",
  "summary": "waiting for a person: Ship this change?"
}
```

## What you can do with it

- **Run a ready-made team on your own files.** A writer and a reviewer, a
  review panel with a threshold, or feature delivery from brief to approval.
  Import one, add your brief and engines, and run it.
  [Ready-made workflows](/packages/builtin-workflows).
- **Give work a shape in one call.** Steps in order, a graph with parallel
  branches, a loop that revises until it passes, a tournament of
  candidates, a quorum of opinions. [Workflows](/concepts/workflows).
- **Say what each step does and what done means.** You write a sentence for
  each. In a `workflow()`, the agent doing the step gets both in its prompt.
  [Workflows](/concepts/workflows).
- **Send work back to the step that owns it.** A failed review names the
  step that must fix it, and the work goes back there with the findings.
  [Sending work back](/concepts/workflows#sending-work-back).
- **Get a second opinion that's really a second opinion.** Before a run
  starts, the workflow builder checks that the implementer and every
  reviewer come from different model families.
  [The runtime workflow builder](/packages/runtime).
- **Stop for a person.** A callback gate puts one decision in front of
  someone, and the run carries on from that step with the answer. With a
  stored callbacks client and a record, a run nobody is watching exits at
  the question and carries on when a schedule starts it again.
  [Callback gates](/reviewing/callback-gates).
- **Approve only what was proved.** An approval is bound to the exact bytes
  and test result it was given. [Proof acceptance](/reviewing/proof-acceptance).
- **Run a step as a command.** The step passes on the exit code, never on a
  model's report. [Workflows](/concepts/workflows).
- **Use the engines you have.** Claude, Codex, Grok, OpenCode, the Agent
  SDK, the Anthropic API, or one you write to the contract.
  [Jev](/packages/engine-jev-api) answers structured questions about a run.
  [Engine contracts](/packages/api).
- **Define agents and skills in markdown.** The files your team already
  writes become the persona and the skills a step runs with.
- **Give each step its own worktree.** A change touches only the paths it
  declared, and a mismatch pauses the run.
  [The workspace contract](/workspace/contract).
- **Keep every step in a file on disk.** Events and artifacts sit side by
  side, with no server or database.
  [How a run is recorded](/recording/how-a-run-is-recorded).
- **Kill a run and start it again where it stopped.** Nothing finished is
  done twice. [The runner](/packages/runner).
- **Give the team a memory.** Keep it in process, in private Git refs or in
  your own Markdown files. The steps curate it and ground their work in it.
  [Memory](/memory).
- **Put a diff in front of a person in their own editor**, or drive runs
  from cmux. [Surfaces](/concepts/surfaces).
- **Let team members talk.** Teammates post messages to rooms that are
  files, and a mention asks the named teammate to take a turn.
  [A team conversation](/workflows/team-conversation).
- **Set a budget and read the cost.** Cap the tokens a run can spend, and
  read its cost report. [The runtime](/concepts/runtime).


## Packages

| Package | Purpose | Version |
| --- | --- | --- |
| `@obversa/obversa` | Installs every package below except Jev | `0.1.0` |
| `@obversa/runtime` | Builds and runs workflows as graphs, team conversations or a review loop | `0.1.0` |
| `@obversa/runner` | Supervises stored graph runs in bounded workers | `0.1.0` |
| `@obversa/api` | Defines every contract: engine, memory, graph, events, artifacts, workspace, callbacks, proofs and run definitions, with their validators | `0.1.0` |

The seven engine plugins, three memory adapters and the notifier each have a
page in the Plugins group. Install the bundle, and add Jev if you need it:

```bash
npm install @obversa/obversa
npm install @obversa/engine-jev-api
```

The api, core, runtime and runner packages always share one version. The
others each keep their own.

The runtime never imports an engine or a memory adapter. You pass the ones
you want when you run.
