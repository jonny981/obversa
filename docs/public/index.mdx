Obversa turns the coding agents you already run into a team: one writes, a
different model reviews, and a person decides what ships.

Think about how a change gets made on a good team. Someone writes it.
Someone else reads it, and if it's wrong, the writer goes again with a note
saying what to fix. A hard call gets a second opinion. The big decisions go
to a person who can say no. And when a laptop dies halfway through, nobody
starts the week again, because the work so far is written down.

Obversa lets you run Claude Code, Codex and the rest that way. You describe
the work as steps: who does each one, where the reviews are, and where a
person decides. Obversa runs it one bounded engine call at a time, and can
write every step down as it happens. Kill a run under the
[supervised runner](/driving/runner) and start it again, and it carries on
from its record. Nothing that finished runs twice.

## Motivation

Agents aren't deterministic. Left to themselves, there's no guarantee that
every step of a process is followed, in the right order, under the right
conditions. Obversa puts a deterministic process around the inference: many
small jobs, each with its own review. The agent's work stays narrow, so each
job spends fewer tokens.

The workflows generated in most coding agent harnesses are internal, and
can't be saved, shared or repeated. Obversa workflows are simple,
harness-agnostic TypeScript files. You save one, share it and run it again,
and the process runs the same way each time.

It models process at every layer: the organisation, the team and the
individual.

## Inference at the leaves

Inference belongs mostly at the leaves. Around each inference step you can
build as much process as you like: deterministic scripts, tools and checks,
so the job an agent has to do is clearer, simpler, better bounded and
cheaper. Squeeze the determinism out of the agents and what's left is a set
of very specific, focused agents doing narrow tasks.

That improves quality. It also means a small open-weight model tuned to a
narrow, well-bounded task can do it as well as a frontier model would, at a
fraction of the cost.

Process engineers call this value stream mapping: understand the process,
then make the steps that don't add direct value cheaper or faster, or cut
them out. Here that means lifting every deterministic step out of the
agents, so their context shrinks to the parts that truly need inference.

## Key concepts

- **[Workflows](/concepts/workflows).** The team as a TypeScript file: the
  steps, who does each one, where the reviews are, and where a person
  decides.
- **[Feedback loops](/concepts/feedback-loops).** A review or a test fails a
  step, and the step runs again with the findings, up to a limit you set.
- **[The record](/concepts/record).** An append-only event log of the run,
  the single source of truth a stopped run carries on from.
- **[Running](/concepts/running).** The runtime runs one bounded step at a
  time. The runner restarts a killed run from its record.
- **[Surfaces](/concepts/surfaces).** One question on a local page in front
  of a person. The run waits for the answer, then the page is gone.
- **[Memory](/concepts/memory).** Files a step can open again later, behind
  one port with an adapter for each place they can live.
- **[Workspace](/concepts/workspace).** A Git worktree per writer, captured
  and verified, so two writers never collide.

## Install

Install the bundle:

```bash Terminal
npm install @obversa/obversa
```

Then say who writes, who reviews, and what a red test does:

```ts examples/teams/writer-reviewer-pair.ts (excerpt) {5-8,22,29}
  return workflow('writer-reviewer-pair', {
    brief: briefFromFile('briefs/add.md'),
    options: { timeout: '10m' },

    roles: {
      write: engines.claude('claude-sonnet-4-5'),
      review: [engines.codex('gpt-5.6-luna')],
    },

    stages: [
      stage('write', {
        agent: 'write',
        writes: ['src/add.mjs', 'test/add.test.mjs'],
        desc: 'Write the function and its test from the brief.',
        gate: 'The files named in the brief exist in the workspace.',
        retry: 1,
      }),
      stage('test', {
        run: ['node', '--test', 'test/add.test.mjs'],
        desc: 'Run the test command against the written files.',
        gate: 'The test command exits 0.',
        sendsBackTo: 'write',
      }),
      stage('review', {
        panel: 'review',
        agree: 1,
        desc: 'Read the code, the test and its result.',
        gate: 'The change meets the brief.',
        sendsBackTo: 'write',
      }),
    ],
  });
```

A Claude seat writes the function and its test from the brief. Node runs
the test, and a red run puts the output in front of the write stage, which
runs again with it. A reviewer on a different model, Codex here, reads the
code and the result, and a rejection goes the same way. `workflow()`
refuses a writer and a reviewer from the same model family before the run
starts. The whole file and a real run are on
[A writer and a reviewer](/patterns/writer-and-reviewer).
