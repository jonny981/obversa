---
title: "Callback gates"
description: "Stop the run for one question a person, an agent or a service must answer, and carry on with the answer."
---


Some steps aren't the agent's to decide. Ship this release? Is this the
migration we meant? Which of these two drafts? On a team, those go to a
person, and the work waits for the answer. A callback gate is that pause.
The workflow asks one question with a fixed shape of answer and stops. When
someone answers, it carries on from that exact step.

The question can go to a person in their browser, to another agent, or to
a service. Whoever answers, the answer must come back in the shape the gate
asked for. The workflow then branches on it without asking a model what the
answer meant.

## What you get

- **One question, one typed answer.** You state the question and the
  shape of the answer, such as `{ approved: boolean }`. The run records
  the answer and branches on it.
- **The run survives the wait.** With the stored callbacks client, the
  question is an event in the run's record, so a process that dies while a
  person is thinking loses nothing. A fresh process rebuilds the pause and
  waits for the same answer.
- **Any answerer.** A router takes the question to whoever answers it: a
  surface in a browser for a person, an engine call for an agent, an API
  call for a service. Swap the router and the question stays the same.
- **Answers bound to what they judged.** An approval can carry the exact
  bytes, proof and workspace state it approved, so a later change can't
  reuse an old yes.

## Two ways to wait

An `approval()` step waits in one of two ways, and both record the question
the same way. A team review that uses a callback gate isn't one of them. It
returns a pause carrying its question straight away, however the run was
started.

Attended: a person is at the run, so the process stays up and waits for the
answer. Set `onCallback: 'wait'` for this mode. It's never the default. A run
exits unless you ask it to wait, whichever callbacks client it's given.

Unattended: nobody is attached, so the run records the question and exits. A
schedule starts the same file again with `resume: true`, and the run reads
its record first. If the answer has arrived, the step carries on. If it
hasn't, the run exits again with the same recorded pause and asks nothing a
second time.

The answer arrives through the stored callbacks client, which you make with
`createStoredCallbackClient`. Pass it to `run()` as `callbacks`. Without it,
`run()` gives each run a fresh in-memory client, and its questions end with
the run. [How a run is recorded](/recording/how-a-run-is-recorded) covers
what else a resumed run skips or repeats.

The only difference between the modes is whether the process stays up.
Nothing in the record says which mode asked the question.

## Source

This is `examples/callback-gate.ts`, byte for byte. Copy it into a project
set up as in [Installation](/get-started/installation), then run it.

```ts
import {
  createCallbackClient,
  createCallbackGate,
  directRouter,
  replayCallbackClient,
  type CallbackGateDefinition,
} from '@obversa/runtime';

const definition: CallbackGateDefinition = {
  gateId: 'release-approval',
  gateVersion: 1,
  decisionText: 'Approve release abc123?',
  responseSchema: {
    type: 'object',
    properties: { approved: { type: 'boolean' } },
    required: ['approved'],
  },
  input: { revision: 'abc123' },
};

const client = createCallbackClient();
const request = createCallbackGate(definition);
client.post(request);

const firstClaim = client.claim(request.requestId, 'router-a');
const blockedClaim = client.claim(request.requestId, 'router-b');
if (!firstClaim.ok) throw new Error('The first router did not claim the request.');
const released = client.release(request.requestId, firstClaim.claimToken);
const submitted = await directRouter(
  client,
  request,
  'router-b',
  () => ({ approved: true }),
);

const sameQuestion = createCallbackGate({
  ...definition,
  presentation: { theme: 'dark' },
});
const changedQuestion = createCallbackGate({
  ...definition,
  input: { revision: 'def456' },
});
const replayed = replayCallbackClient(client.history());

console.log(JSON.stringify({
  requestId: request.requestId,
  digest: request.digest,
  sameQuestionId: sameQuestion.requestId === request.requestId,
  changedQuestionId: changedQuestion.requestId !== request.requestId,
  blockedKind: blockedClaim.ok ? null : blockedClaim.kind,
  released: released.ok,
  submitted: submitted.ok,
  events: client.history(request.requestId).map((event) => event.kind),
  replayedPending: replayed.listPending().length,
}, null, 2));
```

## A person's decision as a step

In the common case of one question in a workflow, `approval` wraps the
gate. It asks through the run's callbacks client. A yes passes the step. A
no sends the work back to the step you name as its `target`, with the
person's note as the finding. No answer pauses the run with the request
pending. [A person decides](/workflows/approval) shows it in a running file.
It's built on the client, the routers and the stored history on this page.
A host answers through the same pieces.

## How it works when it runs

1. The workflow posts the question, and the record gains a
   `callback-requested` event.
2. A router claims it. Two routers can't hold one question at once.
3. The router asks: it opens a surface, calls an agent or calls a service.
4. The router submits the answer. The run checks that the required fields
   are there and have the right types, then records it. Check any deeper
   rule in your host before it submits.
5. The host resumes the paused step with the answer in hand. An answer
   doesn't restart an exited run by itself. The host reads the decision
   first, so it can decide an approval needs a second look.

If the router dies between claim and answer, the question is still there
and still claimed. Once the claim is released with its claim token, another
router can take it.

## Using it in a workflow

Put a gate where a person must say yes: before a release, before a
destructive change, before spending money. Give it a surface and the run
pauses with the question open in a browser. The
[surfaces](/concepts/surfaces) page covers the page itself. For decisions
about a proposed change, bind the approval to the evidence with
[proof acceptance](/reviewing/proof-acceptance).

## Reference: what the request identity covers

The request digest covers the gate id and version, the question text, the
response schema and the input. Change any of them and it's a new question,
so an answer to the old one doesn't carry over. Presentation hints, such as
a theme or a pane placement, are outside it. Changing only how a question
is shown keeps it the same question.

An approval gate can also bind the answer to proof, input artifacts, output
bytes, permissions and a workspace anchor. The host checks those still match
before it acts on the approval.
