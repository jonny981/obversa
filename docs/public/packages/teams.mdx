Write the team as one file that reads top to bottom: the brief, the
roles, the stages in order. Each stage says who does it, what it writes,
who reads it and where the work goes back to. The package compiles that
into the runtime's graph, so a review that fails sends the work back, a
command decides on its exit code, a person's answer is waited for, and
every step is on the record.

```bash
npm install @obversa/runtime @obversa/teams @obversa/engine-claude-cli @obversa/engine-codex
```

## The smallest team

A Claude seat writes the files the brief names, Node runs the test, and a
Codex seat reads the result. A rejection sends the work back to the writer.

```ts
import { claude } from '@obversa/engine-claude-cli';
import { codex } from '@obversa/engine-codex';
import { run } from '@obversa/runtime';
import { fromFile, stage, workflow } from '@obversa/teams';

const team = workflow('writer-reviewer-pair', {
  brief: fromFile('briefs/add.md'),
  options: { timeout: '10m' },

  roles: {
    write: claude('claude-sonnet-4-5'),
    review: [codex('gpt-5.6-luna')],
  },

  stages: [
    stage('write', {
      agent: 'write',
      writes: ['src/add.mjs', 'test/add.test.mjs'],
      desc: 'Write the function and its test from the brief.',
      gate: 'The files named in the brief exist in the workspace.',
      retry: 1,
    }),
    stage('test', {
      run: ['node', '--test', 'test/add.test.mjs'],
      desc: 'Run the test command against the written files.',
      gate: 'The test command exits 0.',
      sendsBackTo: 'write',
    }),
    stage('review', {
      panel: 'review',
      agree: 1,
      desc: 'Read the code, the test and its result.',
      gate: 'The change meets the brief.',
      sendsBackTo: 'write',
    }),
  ],
});

const result = await run(team);
console.log(JSON.stringify(result.outcome, null, 2));
```

A real run of this file, and the files it left behind, are on the
[writer and reviewer](/workflows/writer-and-reviewer) page. The
[review panel](/workflows/review-panel) and
[feature delivery](/workflows/feature-team) pages do the same for the two
larger teams.

## What you get

- **`workflow(name, { brief, roles, stages, options?, post? })`.** The
  team, as a job for `run`. Stages run in the order written, each after
  the one before it.
- **`stage(name, { ... })`.** One step. Exactly one of `agent`, `run`,
  `panel` or `input` says what kind of step it is; the other keys say what
  it writes, who reads it and where the work goes back to.
- **Seats from the engine plugins.** `claude('claude-sonnet-4-5')` from
  `@obversa/engine-claude-cli`, `codex('gpt-5.6-luna')` from
  `@obversa/engine-codex`, `opencode(model, { executable })` from
  `@obversa/engine-opencode-cli`. Each carries the identity the plugin
  records and starts the engine able to write files.
- **`person(question)`.** A role a person fills: the stage that names it
  puts the question to a person and waits for the answer.
- **`fromFile(path)`.** A brief kept as a markdown file beside the code.
  Its body is the brief; front matter may carry `files`, the paths the
  brief expects written.
- **The three ready-made teams,** `writerReviewerPair`, `thresholdPanel`
  and `featureDelivery`, as functions that take seats and return a job.
  They are what the three example files declare, and the shape to copy
  when a workflow file is not what you want.
- **`outcomeFromAgentText`.** The parser the teams use on a reviewer's
  reply: the first JSON decision object becomes a pass, or a revise with
  its findings aimed at the step you name.

## The keys of a stage

| key | what it means |
| --- | --- |
| `agent` | The role that does the work. The stage must say what it `writes`. |
| `run` | A command, one string with no quoting or an array. Exit 0 passes; a red run goes back to `sendsBackTo` with the output as the finding. It may change the files it `writes` and no other declared file; a change to another declared file fails the stage by name. Files nobody declared are not watched. |
| `panel` | A role that is a list of seats. `agree` is how many must accept; the default is all of them. |
| `input` | A person role. The stage asks the question and waits. |
| `writes` | The files this stage writes, relative to the workspace. It writes those and no other declared file. For an agent stage a missing or empty one fails the stage by name; a command stage is judged by its exit code. |
| `desc`, `gate` | What the stage does and what must be true for it to count. Both reach the reviewers and the record. |
| `reviewedBy` | A panel role that reads this stage's work. A rejection runs the stage again with the findings; a note written back unchanged fails plainly. |
| `sendsBackTo` | The earlier stage a rejection or a red run goes back to. A stage cannot send back to itself; use `reviewedBy`. |
| `retry` | How many times this stage may run again: the review restarts of a reviewed stage, or the kickback budget of a stage others send back to. Default 1. It belongs to the stage that repeats. |
| `when` | A condition read before the stage runs: `passed(name)`, `failed(name)`, or an async predicate over `ctx`. A stage whose `when` is not met is recorded as skipped and counts as passed for the stages after it. |
| `optional` | A red run of this stage does not fail the workflow or block the stages after it. `failed(name)` on a later stage is allowed only when the named stage is optional; on a required stage a red run stops the workflow, so there is no other path to choose. |
| `needs` | One or more earlier stage names this stage also depends on, beside the one before it. A condition can then read a stage further back through `passed`, `failed` or `ctx.needs`. A name that is not an earlier stage is an error when the workflow is built. |

## The keys of a workflow

| key | what it means |
| --- | --- |
| `brief` | The work, as text or `fromFile`. Every model in the team reads it. |
| `roles` | Every seat and person, named once. Stages refer to the names. |
| `stages` | The steps, in order. Each needs the one before it. |
| `options.timeout` | A duration such as `'10m'`, applied to every stage. |
| `post.always` | Runs after the graph settles, with the record. |

The workspace is the directory the file runs in.

## Gotchas

- **It ships no command.** You import a workflow and run it from your own
  file.
- **A seat starts its engine unattended, and the two plugins differ.** A
  Codex seat runs sandboxed to the workspace with approvals off. A Claude
  seat runs with permission prompts off, which lets it run any command the
  process can, because the mode that only accepts edits blocks the commands
  a headless run needs. Both take an options object to choose otherwise.
  Run a team in a directory you are willing to let a model change.
- **A reviewer declares a different model family from the writer.** Every
  seat of a `reviewedBy` panel, and of a panel that sends work back to an
  agent stage, must report a different model family from that stage's seat,
  or the workflow is refused before any model runs. What the check compares
  is what each seat reports about itself, so name the seats yourself when
  the second opinion has to come from another provider.
- **`reviewedBy` and `sendsBackTo` are two different returns.** The first
  runs the same stage again; the second goes back to an earlier one. A
  stage uses one or the other.
