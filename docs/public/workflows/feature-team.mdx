---
title: "Feature delivery"
description: "Research, plan, test, review, approve: one brief to an approved change, with each review able to send its work back."
---

Hand a brief to a team and get back an approved change with the evidence
beside it. This file records workspace context, requirements, a plan, tests,
implementation, verification, approval, and learning as separate stages.
Reviewers can send a plan back to planning, tests back to the test writer,
or implementation back to the implementer.

```bash
npm install @obversa/runtime @obversa/teams @obversa/engine-claude-cli @obversa/engine-codex
```

## The file

```ts
import { ClaudeCliEngine } from '@obversa/engine-claude-cli';
import { CodexEngine } from '@obversa/engine-codex';
import { run } from '@obversa/runtime';
import { featureDelivery } from '@obversa/teams';

const workspace = process.cwd();
const analyse = {
  engine: new ClaudeCliEngine({ defaultModel: 'claude-sonnet-4-5', permissionMode: 'bypassPermissions' }),
  identity: {
    adapter: 'claude-cli', provider: 'anthropic', modelFamily: 'claude', model: 'claude-sonnet-4-5',
  },
};
const implement = {
  engine: new CodexEngine({ defaultModel: 'gpt-5.6-luna', permissionMode: 'bypassPermissions' }),
  identity: {
    adapter: 'codex', provider: 'openai', modelFamily: 'gpt', model: 'gpt-5.6-luna',
  },
};
const reviewer = {
  engine: new ClaudeCliEngine({ defaultModel: 'claude-sonnet-4-5', permissionMode: 'bypassPermissions' }),
  identity: {
    adapter: 'claude-cli', provider: 'anthropic', modelFamily: 'claude', model: 'claude-sonnet-4-5',
  },
};
const approve = {
  engine: new ClaudeCliEngine({ defaultModel: 'claude-sonnet-4-5', permissionMode: 'bypassPermissions' }),
  identity: {
    adapter: 'claude-cli', provider: 'anthropic', modelFamily: 'claude', model: 'claude-sonnet-4-5',
  },
};

const team = featureDelivery({
  brief: 'Deliver a pure triple(value) function in src/triple.mjs with a Node test in test/triple.test.mjs.',
  workspace,
  files: ['src/triple.mjs', 'test/triple.test.mjs'],
  testFiles: ['test/triple.test.mjs'],
  test: { command: 'node', args: ['--test', 'test/triple.test.mjs'] },
  analyse,
  implement,
  reviewers: [{ name: 'correctness', seat: reviewer, scope: 'implementation' }],
  reviewThreshold: 1,
  approve,
  maxKickbacks: { plan: 3, 'tests-first': 3, implement: 3 },
});

const result = await run(team, { cwd: workspace });
console.log(JSON.stringify(result.outcome, null, 2));
if (result.outcome.status !== 'pass') process.exitCode = 1;
```

## What a run records

A successful run records eleven named stages in its result.

```json
{
  "status": "pass",
  "summary": "dag \"feature-delivery\": all 11 node(s) green"
}
```

The full result also carries each stage's status, summary, and review data.
The record keeps the context, requirements, plan, tests, implementation,
verification, approval, evidence, and learning artifacts beside the run.

The research stages write these notes:

- `team-output/research-context.md` records the workspace facts needed to plan.
- `team-output/research-requirements.md` records the numbered requirements.
- `team-output/plan.md` records one acceptance check for each requirement.

The implementer wrote `src/triple.mjs`:

```js
export function triple(value) {
  if (typeof value !== 'number' || !Number.isFinite(value)) {
    throw new TypeError('value must be a finite number');
  }

  return value * 3;
}
```

and `test/triple.test.mjs`:

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { triple } from '../src/triple.mjs';

test('triple multiplies finite numbers by three', () => {
  assert.strictEqual(triple(4), 12);
  assert.strictEqual(triple(0), 0);
  assert.strictEqual(triple(-2.5), -7.5);
});

test('triple rejects values that are not finite numbers', () => {
  for (const value of [undefined, null, '4', {}, NaN, Infinity]) {
    assert.throws(() => triple(value), TypeError);
  }
});
```

The approve step writes `team-output/approval.md` with the approval and the
exact marker from `prepare`. The final `close` step writes:

- `team-output/evidence.md` with the marker, start time, verification result, and files.
- `team-output/learning.md` with the workflow lesson recorded by the run.

```md
# Approval

**Status:** Ready to ship

Run marker: `<marker recorded by prepare>`
```

## The team's shape

| step | does | done when |
| --- | --- | --- |
| prepare | Clear an earlier approval and record this run's marker. | No approval note exists and the run marker is recorded. |
| research-context | Record the workspace facts needed to plan the change. | The context note exists and a reviewer accepts it. |
| research-requirements | Turn the brief and context into numbered requirements. | The requirements note exists and a reviewer accepts it. |
| plan | Write one acceptance check for each requirement. | The plan exists and every requirement has a check. |
| plan-review | Review the plan against the requirements. | The review threshold accepts the plan. |
| tests-first | Write the declared tests before implementation. | Every declared test file exists and is not empty. |
| tests-review | Review the tests against the plan. | The review threshold accepts the tests. |
| implement | Write the implementation and repeat after review findings. | The test command passes and the implementation review accepts it. |
| verify | Run the final test command once more. | The final test command exits 0. |
| approve | Record approval with this run's marker. | The approval note carries this run's marker. |
| close | Write evidence and learning notes from the run record. | Both notes are non-empty. |

Each step needs the one before it. A review below `reviewThreshold` sends the
work to its owning step: plan review targets `plan`, test review targets
`tests-first`, and implementation review targets `implement`.

## Gotchas

- **Research and planning write notes only.** The package checks that these
  seats leave the implementation and test files alone. Files that were
  already in the workspace before the run are left alone.
- **The implementer and every reviewer are different model families.** The
  analyse and approve seats are free to share a family with either.
- **The approval is a file and a run marker.** `team-output/approval.md`
  must be non-empty and must carry the marker recorded by `prepare` for this
  run.
- **A writing seat can write anywhere the process can.** The files above
  start their Claude and Codex seats with permission prompts off, which is
  what lets a model write files. Run them in a directory you are willing
  to let a model change, and give a reviewing seat a read-only mode if its
  plugin has one.
