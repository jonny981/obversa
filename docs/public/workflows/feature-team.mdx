---
title: "Feature delivery"
description: "One brief to an approved change through eleven small steps: research with its own reviews, a plan, tests first, an implementation loop held to green tests and a panel, verification, approval, evidence."
---

Hand a brief to a team and get back an approved change with the evidence
beside it, the way a real team ships a feature: research first, a plan
that is reviewed, tests before code, an implementation that repeats with
the reviewers' findings until the tests pass and the panel accepts, one
more verification, an approval, and a record of what happened. Inference
sits at the leaves; everything between the leaves is a check the run can
hold to.

```bash
npm install @obversa/runtime @obversa/teams @obversa/engine-claude-cli @obversa/engine-codex
```

## The file

```ts
import { ClaudeCliEngine } from '@obversa/engine-claude-cli';
import { CodexEngine } from '@obversa/engine-codex';
import { run } from '@obversa/runtime';
import { featureDelivery } from '@obversa/teams';

const workspace = process.cwd();
const analyse = {
  engine: new ClaudeCliEngine({ defaultModel: 'claude-sonnet-4-5', permissionMode: 'bypassPermissions' }),
  identity: {
    adapter: 'claude-cli', provider: 'anthropic', modelFamily: 'claude', model: 'claude-sonnet-4-5',
  },
};
const implement = {
  engine: new CodexEngine({ defaultModel: 'gpt-5.6-luna', permissionMode: 'bypassPermissions' }),
  identity: {
    adapter: 'codex', provider: 'openai', modelFamily: 'gpt', model: 'gpt-5.6-luna',
  },
};
const reviewer = {
  engine: new ClaudeCliEngine({ defaultModel: 'claude-sonnet-4-5', permissionMode: 'bypassPermissions' }),
  identity: {
    adapter: 'claude-cli', provider: 'anthropic', modelFamily: 'claude', model: 'claude-sonnet-4-5',
  },
};
const approve = {
  engine: new ClaudeCliEngine({ defaultModel: 'claude-sonnet-4-5', permissionMode: 'bypassPermissions' }),
  identity: {
    adapter: 'claude-cli', provider: 'anthropic', modelFamily: 'claude', model: 'claude-sonnet-4-5',
  },
};

const team = featureDelivery({
  brief: 'Deliver a pure triple(value) function in src/triple.mjs with a Node test in test/triple.test.mjs.',
  workspace,
  files: ['src/triple.mjs', 'test/triple.test.mjs'],
  testFiles: ['test/triple.test.mjs'],
  test: { command: 'node', args: ['--test', 'test/triple.test.mjs'] },
  analyse,
  implement,
  reviewers: [{ name: 'correctness', seat: reviewer, scope: 'implementation' }],
  reviewThreshold: 1,
  approve,
  maxKickbacks: { plan: 3, 'tests-first': 3, implement: 3 },
});

const result = await run(team, {
  cwd: workspace,
  recordTo: 'team-output/events.jsonl',
});
console.log(JSON.stringify(result.outcome, null, 2));
if (result.outcome.status !== 'pass') process.exitCode = 1;
```

A writing seat can write anywhere the process can: the file starts its
Claude and Codex seats with permission prompts off, which is what lets a
model write files. Run it in a directory you are willing to let a model
change. `recordTo` writes every event of the run to a file as it happens.

## The team's shape

Eleven steps, each needing the one before it. Four of them are loops:
the two research steps and the plan repeat until a reviewer accepts the
note, and the implementation step repeats until the test command exits 0
and the panel accepts, three cycles at most. A rejected plan, test or
implementation goes back to the step that owns it with the reviewer's
findings, each target with its own budget.

| step | does | done when |
| --- | --- | --- |
| prepare | Clear any approval left by an earlier run and mark the start of this one. | No approval note exists and the run marker is recorded. |
| research-context | Read the workspace and write down what the change touches, until a reviewer accepts the note. | The context note is in the workspace and a reviewer has accepted it. |
| research-requirements | Turn the brief and the context note into requirements, one REQ-n per line, each testable and traced to the brief. | Every requirement is testable, traces to the brief, and asks for nothing the brief does not. |
| plan | Write an executable plan from the requirements, one acceptance check per job. | Every requirement has a check in the plan and no check asks for more than its requirement. |
| plan-review | Have the reviewers read the plan against the requirements and send it back if it falls short. | At least the threshold number of reviewers have accepted the plan. |
| tests-first | Write the declared test files from the accepted plan before any implementation exists. | Every declared test file exists and is not empty. |
| tests-review | Have the reviewers check that the tests cover the plan and that any red test is red for a stated reason. | At least the threshold number of reviewers have accepted the tests. |
| implement | Write the code to the plan and the tests, run the test command, and repeat with the reviewers' findings until it passes. | The test command exits 0 and the reviewers have accepted the change, within three cycles. |
| verify | Run the test command once more on the final files. | The final test command exits 0. |
| approve | Record that the verified change is ready to ship. | An approval note carrying this run's marker is in the workspace. |
| close | Write the evidence of the run and what was learned, from the record alone. | The evidence note and the learning note are in the workspace. |

Where a step's gate names a file, the package checks the file after the
job. Where it names an exit code, the command decides. Where it names a
reviewer, the reviewer's decision file decides. A model's own report of
its work never passes a step.

## Gotchas

- **Tests come first and may be red.** The `testFiles` you declare are
  written from the plan before any implementation exists. The tests-review
  step asks the reviewers whether a red test is red for a stated reason;
  the implement step is what turns it green.
- **Requirements carry ids.** Every requirement line carries `REQ-n`, every
  check in the plan names the requirement it covers, and the plan step
  compares the two sets. A plan that misses one goes back to its writer
  with the missing ids named; a requirements note with no ids goes back to
  its own writer.
- **A note that comes back unchanged fails.** A writer sent its review's
  findings must rewrite the note; the same bytes again end the loop with a
  plain summary instead of a second identical review.
- **A stale approval cannot pass a new run.** The prepare step removes the
  approval note, and the approve step writes one carrying this run's
  marker. An approval from yesterday is not an approval today.
- **The implementer and every reviewer are different model families.** The
  research, plan and approve seats are free to share a family with either.
- **A reviewer's decision is its file.** Each reviewer writes
  `reviews/<name>.json`; the team reads that file first and the reply
  second. A reply with no decision in either is asked for once more, then
  the review stops with a plain summary rather than a rejection of the
  work.
- **A writing seat can write anywhere the process can.** Run the file in a
  directory you are willing to let a model change.
