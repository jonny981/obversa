---
title: "Feature delivery"
description: "One brief to a change a person is asked to ship, in nine small steps: research with its own reviews, a plan, tests first, an implementation held to green tests and a panel, a person's decision, evidence."
---

Hand a brief to a team and get back a change ready for a person to ship,
the way a real team delivers a feature: research first, each note
reviewed; a plan that is reviewed; tests before code; an implementation
that runs again with the reviewers' findings until the tests pass and the
panel accepts; then the question to a person, and the evidence written
from the record. Inference sits at the leaves; everything between the
leaves is a check the run can hold to. The whole team is one file that
reads top to bottom.

```bash
npm install @obversa/runtime @obversa/teams @obversa/engine-claude-cli @obversa/engine-codex
```

## The file

```ts
import { claude } from '@obversa/engine-claude-cli';
import { codex } from '@obversa/engine-codex';
import { run } from '@obversa/runtime';
import { fromFile, person, stage, workflow } from '@obversa/teams';

/**
 * A feature, delivered the way a team delivers one. The roles are named once;
 * every stage is a small block of nouns: who does it, what it writes, who
 * reads it, where a red result goes back to. Inference happens only where a
 * role is named; every other stage is a command or a person.
 */
const team = workflow('feature-delivery', {
  brief: fromFile('briefs/triple.md'),
  options: { timeout: '10m' },

  roles: {
    analyse: claude('claude-sonnet-4-5'),
    implement: codex('gpt-5.6-luna'),
    review: [claude('claude-sonnet-4-5'), codex('gpt-5.6-luna')],
    approve: person('Ship this change?'),
  },

  stages: [
    stage('research-context', {
      agent: 'analyse',
      writes: 'team-output/research-context.md',
      desc: 'Read the workspace and write down what the change touches.',
      gate: 'The context note is in the workspace and a reviewer has accepted it.',
      reviewedBy: 'review',
      retry: 3,
    }),

    stage('research-requirements', {
      agent: 'analyse',
      writes: 'team-output/research-requirements.md',
      desc: 'Turn the brief and the context note into requirements, one REQ-n per line.',
      gate: 'The requirements note is in the workspace and a reviewer has accepted it.',
      reviewedBy: 'review',
      retry: 3,
    }),

    stage('plan', {
      agent: 'analyse',
      writes: 'team-output/plan.md',
      desc: 'Write an executable plan from the requirements, one check per REQ-n.',
      gate: 'Every requirement has a check in the plan.',
      reviewedBy: 'review',
      retry: 3,
    }),

    stage('tests-first', {
      agent: 'implement',
      writes: 'test/triple.test.mjs',
      desc: 'Write the declared test files from the accepted plan before any implementation exists.',
      gate: 'Every declared test file exists and covers the plan.',
      reviewedBy: 'review',
      retry: 3,
    }),

    stage('implement', {
      agent: 'implement',
      writes: 'src/triple.mjs',
      desc: 'Write the code to the plan and the tests.',
      gate: 'The source file exists.',
      retry: 3,
    }),

    stage('test', {
      run: ['node', '--test', 'test/triple.test.mjs'],
      desc: 'Run the tests; a red run goes back to implement with the output.',
      gate: 'The test command exits 0.',
      sendsBackTo: 'implement',
    }),

    stage('review', {
      panel: 'review',
      agree: 1,
      desc: 'Read the change and the test result against the plan.',
      sendsBackTo: 'implement',
    }),

    stage('approve', {
      input: 'approve',
      desc: 'Put the verified change in front of a person.',
      gate: 'A person has said yes.',
    }),

    stage('close', {
      agent: 'analyse',
      writes: ['team-output/evidence.md', 'team-output/learning.md'],
      desc: 'Write the evidence of the run and what was learned, from the record alone.',
      gate: 'Both notes are in the workspace.',
    }),
  ],

});

const result = await run(team);
console.log(JSON.stringify(result.outcome, null, 2));
```

A writing seat can write anywhere the process can: the seat helpers start
their engines with permission prompts off, which is what lets a model
write files. Run it in a directory you are willing to let a model change.
`recordTo` writes every event of the run to a file as it happens.

## The team's shape

Nine stages, each needing the one before it. A reviewed stage runs again
with the reviewer's findings until the review accepts, a red test or a
rejected review sends the work back to the stage it names, and each
stage that repeats carries its own `retry`.

| step | does | done when |
| --- | --- | --- |
| research-context | Read the workspace and write down what the change touches. | The context note is in the workspace and a reviewer has accepted it. |
| research-requirements | Turn the brief and the context note into requirements, one REQ-n per line. | The requirements note is in the workspace and a reviewer has accepted it. |
| plan | Write an executable plan from the requirements, one check per REQ-n. | Every requirement has a check in the plan. |
| tests-first | Write the declared test files from the accepted plan before any implementation exists. | Every declared test file exists and covers the plan. |
| implement | Write the code to the plan and the tests. | The source file exists. |
| test | Run the tests; a red run goes back to implement with the output. | The test command exits 0. |
| review | Read the change and the test result against the plan. | A person has said yes. |
| approve | Put the verified change in front of a person. | A person has said yes. |
| close | Write the evidence of the run and what was learned, from the record alone. | Both notes are in the workspace. |

Where a stage's gate names a file, the package checks the file after the
job. Where it names an exit code, the command decides. Where it names a
reviewer, the reviewer's decision decides. A model's own report of its
work never passes a stage.

## Gotchas

- **Tests come first and may be red.** The tests-first stage writes the
  test file from the plan before any implementation exists; its review
  asks whether a red test is red for a stated reason, and the implement
  stage is what turns it green.
- **A stage writes what it declares and nothing else.** `writes` names the
  files a stage may write; a stage that touches another declared file
  fails by name, so the tests-first stage cannot write the implementation.
- **A note that comes back unchanged fails.** A writer sent its review's
  findings must rewrite the note; the same bytes again end the stage with
  a plain summary instead of a second identical review.
- **The implementer and every reviewer are different model families.** The
  analyse seat is free to share a family with either.
- **A reviewer's decision is its file.** Each reviewer writes
  `reviews/<name>.json`; the team reads that file first and the reply
  second. A reply with no decision in either is asked for once more, then
  the review stops with a plain summary rather than a rejection of the
  work.
- **A person's answer is not in the file.** The run pauses at `approve`
  with the question pending. [A person decides](/workflows/approval) shows
  how a stored callbacks client carries the answer into the next run.
- **A writing seat can write anywhere the process can.** Run the file in a
  directory you are willing to let a model change.
