Every team has a way work moves. A ticket gets read, someone builds it,
someone tests it, a few people review it, and a lead says ship. Nobody draws
that on a whiteboard before each ticket. It's just how the team works. A
workflow is that shape, written down once so the runtime can run it for
your agents the same way every time.

You write a workflow in TypeScript, in one file, with the steps in the order
they run and the reviews where they belong. The runtime runs it one bounded
step at a time and records each step as it finishes, so the shape you wrote
is also the record you get back.

## What a workflow is made of

- **Steps.** Each step is a job: an agent call, a script, a check. A step
  has a name, and the record carries whose work each step was.
- **Sequence and dependencies.** A pipeline runs steps one after another. A
  graph runs independent steps together and waits where one depends on
  another. Both are one call.
- **Reviews.** A review is a step that judges another step's result. A
  panel passes on the count you set. A reviewer that fails a step names
  the stage that must fix it, and the work goes back there with the
  findings.
- **Decisions for a person.** A callback gate stops the run, puts one
  question in front of someone, and continues from that step with the
  answer.
- **Limits.** An attempt can carry a time budget, and work goes back only
  as many times as you allow. An overrun is a result you can read, not a
  hang.

## Say what each step is for, beside the code

A step can carry two sentences next to its job: `desc`, what the step does,
and `gate`, what done means for it. Both are optional. Both go into the
plan the runtime prints and into the record. An agent step built with
`graphContext: true` also gets `desc` in its prompt. In a `workflow()`, the
writing seat gets both. A criterion written beside the code is much harder
to write vaguely. `needs` takes a single name when a step has one
dependency, which is the common case.

```ts
/**
 * A small team in DAG form. Each stage says what it does and what done means.
 * It runs offline, so the example needs no model or network.
 */
import {
  dag,
  fnJob,
  jobMeta,
  renderPlan,
  run,
  type Outcome,
} from '@obversa/runtime';

function stage(name: string, summary: string) {
  return fnJob(name, async (): Promise<Outcome> => ({
    status: 'pass',
    summary,
  }));
}

const describedTeam = dag({
  name: 'described-team',
  nodes: {
    brief: {
      desc: 'Turn the request into a short delivery brief.',
      gate: 'The brief names the user, outcome, and constraints.',
      job: stage('brief', 'brief ready'),
    },
    build: {
      needs: 'brief',
      desc: 'Build the smallest useful change from the brief.',
      gate: 'The change meets the brief and its checks pass.',
      job: stage('build', 'change built'),
    },
    review: {
      needs: 'build',
      desc: 'Check the change before it reaches the user.',
      gate: 'The change is safe to release and easy to explain.',
      job: stage('review', 'review complete'),
    },
  },
});

const result = await run(describedTeam);
const report = {
  plan: renderPlan(jobMeta(describedTeam)).join('\n'),
  status: result.outcome.status,
};
console.log(JSON.stringify(report, null, 2));

if (result.outcome.status !== 'pass') process.exitCode = 1;
```

The plan the runtime renders shows both sentences under each step:

```text
{
  "plan": "dag \"described-team\" (3 nodes)\n  - brief\n      desc: Turn the request into a short delivery brief.\n      gate: The brief names the user, outcome, and constraints.\n      fn \"brief\"\n  - build (needs brief)\n      desc: Build the smallest useful change from the brief.\n      gate: The change meets the brief and its checks pass.\n      fn \"build\"\n  - review (needs build)\n      desc: Check the change before it reaches the user.\n      gate: The change is safe to release and easy to explain.\n      fn \"review\"",
  "status": "pass"
}
```

## A feature team, in one file

The file has five named stages. The review is a panel of three that passes
on two. When it fails, the work goes back to the implement stage, not to
the start of the run. The whole file is on the
[first run](/get-started/first-run) page. Copy it from there.

Run it and the panel fails the first attempt, implement runs again, and the
second attempt passes:

```text
{
  "status": "pass",
  "implementRuns": 2
}
```

The stages in that file are small functions, so the shape is the only thing
on show. In a real team each one calls an engine, and the file doesn't
change shape when it does.

## What happens when it runs

The runtime reads the workflow, runs the first step it can, and appends an
event when the step finishes. Then the next. A review that fails a step
appends the findings and the name of the stage to fix, and the runtime runs
that stage again with them. A gate that waits for a person appends the
pause, and the run stops there until the answer arrives. With `recordTo`
set, each of those events is a line in a file on disk. To carry on a
stopped run built with `workflow()`, run it again with `resume: true`, and
it picks up from the record at `recordTo`.
[How a run is recorded](/recording/how-a-run-is-recorded) says what the
file holds and which stages run again.

## Sending work back

Work goes back to the step that owns the fix when a review, a command or a
person says no. You name that step as the `target`:

- **A review panel** needs a `target`, or a failing panel fails the run
  instead of returning the work. The five-stage file on
  [first run](/get-started/first-run) sets it. A panel passes when enough
  reviewers accept, so one that passes on two of three still passes when
  one reviewer fails. To let one voice send the work back, set the pass
  count to the number of reviewers.
- **A command** sends its captured output back when it goes red, with no
  agent in between: `commandJob(label, command, { target })`.
- **A person** answers one question with
  `approval(label, { question, target })`. A no goes back to `target` with
  the person's note as the finding. [A person decides](/workflows/approval)
  shows it.

`maxKickbacks` sets how many times work can go back. Without it, a graph or
pipeline never sends work back. `workflow()` sets it for you from each
target's `retry`. A number is one budget for the whole graph. A map,
`{ plan: 3, 'tests-first': 3 }`, gives each target its own, so a review that
spends its budget on one step can't starve another. A target the map
doesn't name gets none. When a budget runs out, the run fails with the last
findings instead of looping, and every request is in the record with its
count and its limit.

A command can also choose the path instead of sending work back. A node's
`when` reads the outcome of a step it needs with `passed(name)` or
`failed(name)`, so a command's exit code decides which branch runs.
[A command decides the path](/workflows/command-kickback) shows both.

## Shapes you can start from

- A **pipeline** for work that goes in one direction.
- A **review loop** for draft, review, and revise until it passes or runs
  out of tries.
- A **panel** for several reviewers and a threshold.
- A **tournament** for several candidates and one winner.
- A **graph** for anything with parallel branches.

[The examples](/workflows) are complete programs for the common shapes.
Copy one and change the parts that name your team. To write a shape of your
own over the public contract, see
[writing workflow shapes](/graphs/contract).

## Where definitions live

A workflow is source code. Keep it in the repository it works on, in a
shared repository, or in a package. Version it, review it and share it like
anything else you write.
