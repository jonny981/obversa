---
title: "Surfaces"
description: "Pause a run and put an interactive micro UI in front of a person, then carry on with what they tell you."
---


Sometimes a workflow reaches a step no agent should decide alone: approve
this change, pick one of these two drafts, confirm the migration. You want
that one question in front of a person, in a browser, and you want the
answer back in the run. That is what a surface is: a micro UI, one small
web page that pauses the run until a person has had their say.

The surfacer package runs it. You give it the page files and the API the
page calls. It serves them on a private port on your own machine, opens the
page, waits for the person, and hands back whatever they gave you. Then it
is gone. No server to deploy, no accounts, nothing left running.

## What you get

- **Disposable by design.** A surface is a short session, not a viewer. It
  opens for one pause in one run and closes when that pause is over. There
  is no long-lived page to manage, nothing to redeploy when it changes, and
  nothing left running when the run moves on.
- **A pause for a person, not a prompt.** The run stops, the micro UI
  opens, and it waits. What comes back is whatever the page collected: an
  approval, answers to a dozen fields, a whole code review with comments
  anchored to lines. You decide what the page asks and what the answer
  looks like.
- **It always ends, and it ends once.** The person finishes, cancels, the
  time runs out, or you stop it. Every one of those gives you a result, so
  a run never hangs on a person who walked away.
- **Private by default.** The page lives on a loopback address with a
  token in its URL, and every request has to carry it. Nothing on your
  network can reach it, and a page from another origin cannot call it.
- **Your page, your API.** A surface is plain HTML and a few JSON routes
  you write. There is no framework to learn and nothing to install in the
  browser.
- **Secrets stay out.** Answers pass through secret redaction before they
  reach you, unless you say a specific answer must come through byte for
  byte, such as a review comment that quotes code.

## Run one

The review surface ships in `@obversa/source`. It opens your git diff in a
browser, you comment on the lines you care about, you approve or reject,
and the command prints what you did.

```sh
obversa-review --range main..HEAD
```

The answer is not a yes or a no. It is your decision and every comment you
left, each one anchored to a file and a line, carrying any replies an agent
has already made to it:

```json
{
  "decision": "changes-requested",
  "annotations": [
    {
      "anchor": { "target": "src/git.mjs", "side": "new", "position": 42 },
      "body": "Reject an empty range here too.",
      "thread": [
        { "author": { "kind": "agent", "id": "fixer" },
          "body": "Done: the empty range is refused with its own message." }
      ]
    }
  ]
}
```

A run that opened that surface now has a code review in hand, in a shape it
can act on, without a service or an account anywhere. The
[review command](/hosts/review) page has the full result shape and the
other ways to select a diff.

Your own surface is the same shape: you supply the page files and the JSON
routes the page calls, and you call `session.complete` with whatever the
person gave you. The [surfacer reference](/packages/surfacer) has the
contract.

## Use cases

- **Code review.** A diff, inline comments, a decision. The example above.
- **Approval before something irreversible.** Merging, migrating, spending.
  [Callback gates](/reviewing/callback-gates) is the step that waits;
  [approval](/workflows/approval) shows one in a team.
- **A choice between agent outputs.** Two drafts, two plans, two patches.
  The page returns the one a person picked.
- **A form nobody wants to script.** Credentials a machine must not hold, a
  judgement call with six fields.

Same session every time. Only the page changes.

## Use it in a workflow

A callback gate is the step that waits for a person. Give it a surface and
the run pauses at that step, opens the page, and resumes with the answer:
approved, rejected, or a value the page collected. The
[callback gates](/reviewing/callback-gates) page shows the gate; the surface
is the thing the gate opens.

The review page that ships with the source package is a surface: it opens a
diff for inline comments and returns the annotations as the answer. The
[review command](/hosts/review) page shows it.

## Where the page opens

By default the surface opens in your default browser. Inside cmux it opens
as a split beside your terminal, so the question appears next to the run
that asked it. The [cmux host](/hosts/cmux) page shows how, and the
[plugins](/plugins) page lists the hosts.

## Gotchas

- **You cannot hand the link to someone else.** The page only exists on
  the machine that started the run. If the decision belongs to a colleague,
  it has to reach them another way.
- **The lease.** A surface waits for a person, and people walk away. Set
  `leaseTimeoutMs` to how long the question may stand; when it passes, the
  result says so and the run continues on that.
- **The acknowledgement.** The browser confirms it received the decision
  before the session closes. A page that answers and closes itself without
  the acknowledgement call looks, to the run, like a page that never
  answered, until the acknowledgement timeout ends it.
- **Inline scripts.** The page's content policy allows no inline script or
  style; ship them as files.
- **Verbatim answers.** If an answer must survive exactly, quoting code for
  example, complete it with `verbatim: true`. Everything else is redacted,
  and that is the safe default.
