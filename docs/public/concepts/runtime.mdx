---
title: "The runtime"
description: "One package runs your workflows one bounded step at a time, and can write every step to a record you own."
---


When you hand work to a team, you don't stand over each person. You say
what the steps are and who takes each one, and you look at the log when
it's done. The runtime is the part of Obversa that stands over the steps
for you. It's one package, `@obversa/runtime`.

## What it does for you

- **Runs the shape you wrote.** It runs a pipeline, a review loop, a panel,
  a tournament or a graph of your own. It decides what runs next, never
  what the work means.
- **Enforces your limits.** When an attempt runs out of time or tries, you
  get a result you can read instead of a hang.
- **Keeps the record.** When you ask for a record, every step appends an
  event to it. That record is the run's state, and there is no other.
- **Stays out of your tools.** The runtime imports no engine and no memory
  adapter. Your program hands it the ones you chose, and it runs where your
  repositories are. Hand in an engine for every agent step. The offline
  examples use plain functions or a mock engine instead.

## See it run

model behind it. It prints one report: what completed, in what order, and
the digest of the plan it ran.

## How a run is kept honest

A stored run keeps the workflow it was given and the plan it resolved from
it: the engines, the permissions, the contracts. To use an edit to the
workflow, start a new run. A fresh executor checks the stored plan before
it runs anything. The state of a run is only ever rebuilt from its events,
so replaying a record never calls an engine and never repeats finished
work.

## What the runtime is not

It's a library, not a service. It runs when your program calls it and stops
when the run ends. The runner package's supervised run restarts a killed
run for you. [How a run is recorded](/recording/how-a-run-is-recorded) says
which layer does what.
