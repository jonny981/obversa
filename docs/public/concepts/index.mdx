description: "Give your agents the shape of a real team: named roles, reviews that send work back, and a person to answer to."

Think about how a change gets made on a good team. Someone writes it.
Someone else reads it, and if it is wrong, sends it back to the person who
wrote it with a note saying what to fix. A hard call gets a second opinion.
The big decisions go to a person who can say no. And when a laptop dies
halfway through, nobody starts the week again, because the work so far is
written down.

Obversa lets you run your agents that way. You describe the work as steps,
say who does each one, where the reviews are, and where a person decides.
Obversa runs it, one bounded engine call at a time, and writes down every
step as it happens. Run it under the supervised runner, kill it, start it
again, and it carries on from the record with nothing already finished
done twice.

## Why it exists

Agents are not deterministic. Left to themselves, there is no guarantee
that every step of a process is followed, in the right order, under the
right conditions. Obversa puts a deterministic process around the
inference: many small jobs, each with a review cycle, so the research, the
implementation and the tests are each checked before the next step runs.

The workflows built into a frontier harness cannot be saved, shared or
repeated. An Obversa workflow is a file. You save it, share it, and run it
again, and it runs the same way each time.

It models process at every layer: the organisation, the team and the
individual. Agent frameworks give you one clever session; workflow engines
give you durable steps and a server. Neither gives you a team with a
process, and that is the layer Obversa owns.

## Inference at the leaves

Inference belongs mostly at the leaves. Around each inference step you can
build as much process as you like: deterministic scripts, tools and checks,
so that the job an agent has to do is clearer, simpler, better bounded and
cheaper. Squeeze the determinism out of the agents and what is left is a
set of very specific, focused agents doing narrow tasks.

That improves quality, and it does something else: a narrow, well-bounded
task can be done by a small open-weight model tuned to it, as well as a
frontier model would, at a fraction of the cost.

Process engineers call the method value stream mapping: understand the
process, then make the steps that add no value cheaper, faster, or cut
them out. The same idea applies here. Lift every deterministic step out of
the agents, so their context shrinks to the parts that truly need
inference.


## What you can do with it

- **Run a ready-made team on your own files.** A writer and a reviewer, a
  review panel with a threshold, or feature delivery from brief to approval:
  one import, your brief, your engines, run.
  [The teams package](/packages/teams).
- **Give work a shape in one call.** Steps in order, a graph with parallel
  branches, a loop that revises until it passes, a tournament of
  candidates, a quorum of opinions. [Workflows](/concepts/workflows).
- **Say what each step does and what done means.** A sentence for each on
  the node, and the reviewer judges against it.
  [Workflows](/concepts/workflows).
- **Send work back to the step that owns it.** A failed review names the
  step that must fix it, and the work goes back there with the findings.
  [A review that sends work back](/reviewing/review-loop).
- **Get a second opinion that is really a second opinion.** The implementer
  and every reviewer run on different model families, checked before a run.
  [The teams package](/packages/teams).
- **Stop for a person.** A callback gate puts one decision in front of
  someone and the run carries on from that step with the answer.
  [Callback gates](/reviewing/callback-gates).
- **Approve only what was proved.** An approval is bound to the exact bytes
  and test result it was given. [Proof acceptance](/reviewing/proof-acceptance).
- **Run a step as a command.** The step passes on the exit code, never on a
  model's report. [Workflows](/concepts/workflows).
- **Use the engines you have.** Claude, Codex, Grok, OpenCode, the Agent
  SDK, the Anthropic API, or one you write to the contract.
  [Engines](/packages/engine).
- **Define agents and skills in markdown.** The files your team already
  writes become the persona and the skills a step runs with.
  [Workflows](/concepts/workflows).
- **Give each step its own worktree.** A change touches only the paths it
  declared, and a mismatch pauses the run.
  [The workspace contract](/workspace/contract).
- **Keep every step in a file on disk.** Events and artifacts beside each
  other, no server and no database.
  [How a run is recorded](/recording/how-a-run-is-recorded).
- **Kill a run and start it again where it stopped.** Nothing finished is
  done twice. [The runner](/packages/runner).
- **Give the team a memory.** In process or in private git refs, curated
  and grounded by the steps themselves. [Memory](/memory).
- **Put a diff in front of a person in their own editor.** Or drive runs
  from cmux. [Surfaces](/concepts/surfaces).
- **Let team members talk.** Messages, mentions, and a teammate woken by
  name, in rooms that are files.
  [A team conversation](/workflows/team-conversation).
- **Set a budget and read the cost.** A cap on an attempt and a cost report
  for the run. [The runtime](/concepts/runtime).


## See a team run

Five named stages, the way a real team ships a feature. The review is a
panel of three. Two of the three fail the first attempt, so the panel sends
the work back to `implement` with their findings, and the second attempt
passes. No model and no network: every stage here is a small function, so
the shape of the team is the only thing on show.

```ts
import { fnJob, pipeline, reviewPanel, run, type Outcome } from '@obversa/runtime';
```

```ts
const review = reviewPanel({
  label: 'review',
  reviewers: [
    { name: 'correctness', job: checks.correctness },
    { name: 'safety', job: checks.safety },
    { name: 'scope', job: checks.scope },
  ],
  pass: 2, // two of three agree and the step passes
  target: 'implement', // a failing panel sends the work back here
});

export const featureDelivery = pipeline(
  'feature-delivery',
  [
    { name: 'analyse', job: analyse },
    { name: 'implement', job: implement },
    { name: 'test', job: testStage },
    { name: 'review', job: review },
    { name: 'approve', job: approve },
  ],
  { maxKickbacks: 2 },
);
```

Write many small jobs, each with its own review, for the specific research,
implementation and test tasks in your process, rather than a few large
ones. A coarse step hands the whole task to one inference and hopes. A
small step with a review cycle is a process the run can hold to, and the
team above is the shape to grow, not the size to stop at.

It prints:

```text
{
  "status": "pass",
  "implementRuns": 2
}
```

`implement` ran twice. That second run is the whole point: a reviewer said
no, named the stage that owns the fix, and the work went back there instead
of the run starting over. The whole file is
[feature-team.ts](/concepts/workflows), and the
[the examples](/workflows) has more to copy.

## The words you will meet

Four words carry most of the docs, and each has a page:

- A **workflow** is the shape of the work: the steps and what depends on
  what. [Workflows](/concepts/workflows).
- An **order** is the change you want made; the workflow works on it.
  [Orders](/concepts/orders).
- A **review** is a step that judges another step's result and can send it
  back. [Reviews](/reviewing/callback-gates).
- The **record** is the file of events a run writes as it goes, and what
  the supervised runner reads to restart a killed run where it stopped.
  [How a run is recorded](/recording/how-a-run-is-recorded).

## Things to know before you start

- **It is a library, not a service.** You write a TypeScript file and run
  it with Node. There is no daemon and no dashboard to sign into.
- **The mock engine is for the shape, not the work.** Every example runs
  offline so you can see the mechanics; a real engine plugin makes it do
  real work, and that is one line to change.
- **A plain run does not resume.** Resume belongs to the supervised runner;
  the [recording](/recording/how-a-run-is-recorded) page says which layer
  does what, so you are not surprised by it.
