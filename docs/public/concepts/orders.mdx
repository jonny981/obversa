Someone asks for a change: a passkey login, a report export with a header
row, a landing page redesign. On a team that is a ticket, and the ticket
carries what the person doing the work needs: what is wanted, why, the
designs, the constraints, and what "done" looks like. An order is that
ticket. A workflow is what the team does with it.

## What the runtime does with an order

Nothing, on purpose. The runtime runs workflows and records what they do;
it has no order type, no ticket store and no opinion about where your
tickets live. Your application decides what an order contains, where it is
kept, and which workflow runs on it. That keeps Linear, GitHub, a document
or a text file all equally good places for an order to come from.

## What travels with one

Four things, and the record links them so a reader can understand a result
without reading an agent's conversation:

- **Context.** The requirements, designs and constraints the work needs.
- **The workflow.** The steps that carry it out, as code.
- **The output.** The files and artifacts the work made or changed.
- **The evidence.** The checks, reviews and decisions that accepted the
  output, each bound to the exact bytes it judged.

## One order at a time

Keep an order small enough to follow from request to result. One order
moves through its workflow without waiting for others, gets its reviews
and its human decisions on the way, and closes when its evidence says the
requirements are met. A large piece of work is several orders, each with a
short path to feedback.

## An order's route

Some orders need more than one workflow: a payment feature might pass
through implementation, a security review and a release. The route is that
list. Your application expresses it as a graph whose nodes start the
workflows, so the dependencies decide the order and independent workflows
run together.

## Where the work happens

An order's workflow can run in its own copy of the repository, so two
writers never collide. The runtime's [workspace contract](/workspace/contract)
captures, verifies, leases and forks one Git repository for that; the
[cmux host](/hosts/cmux) opens the order's project worktree beside a shared
one for reusable context.
