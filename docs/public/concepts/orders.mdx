---
title: "Orders"
description: "An Order is the product: the change that flows through a production line until it is complete."
---

An Order is the product that your factory makes.

An Order is a change that you want. Examples: a landing page redesign, a
passkey feature, or a continuous check of conversion data.

## You set the scope

You decide what one Order contains. An Order can be one small fix. An Order
can be one large feature across many repositories. The system does not give
an Order a fixed shape.

Physical products have a fixed shape because physical tools are costly.
Software products do not have this limit. Thus the Order stays fluid.

## One-piece flow

A physical production line usually makes products in batches. Batches exist
because a tool change on a physical line has a high cost.

A software line does not have this limit. Your line can flow one Order at a
time, from start to completion. Short flow gives you fast feedback and a
small work-in-progress count.

## The life of an Order

1. You raise an Order. You give it Context: requirements, designs, and
   constraints.
2. A production line works the Order through its stations.
3. A callback gate can hold the Order until an answerer supplies a result.
4. Evidence attaches to the Order at each important point.
5. The Order closes when the work is complete and the Evidence shows it.

## An Order declares its route

An Order can declare the production lines that it must pass through. This
declaration is the Order's route.

A route is a requirement, not a schedule. The factory satisfies the route.
Lines that do not depend on each other can run in a different order or at
the same time.

Example: an Order for a payment feature declares three lines. It must pass
the implementation line, the security review line, and the release line. The
Order is complete when each declared line is complete and the Evidence shows
it.

In a physical factory, this declaration is the route card that moves with a
work order. It lists the operations that the product must visit.

## What travels with an Order

An Order keeps its records together:

- **Context**: what the factory must know.
- **Process**: the line definition that works the Order.
- **Output**: the files and artifacts that the factory made or changed.
- **Evidence**: the proof that the Output satisfies the Order.

Each Order also gets an isolated workspace with two worktrees. One worktree
holds the project source. One worktree holds the shared context and process
that many projects use.
