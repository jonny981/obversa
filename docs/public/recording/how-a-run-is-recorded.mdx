---
title: "How a run is recorded"
description: "A run appends each event to its record as it happens, and a stopped run can carry on from that record."
---

A run leaves a record as it works. A plain `run()` appends its events to one
file, where you point `recordTo`. A run under the supervised runner keeps its
own store and restarts from it. The store holds the run's definition, its
events and a directory of artifacts.

## What a record looks like

Run `examples/offline-review.ts`, then open the file it wrote. The report
names the file relative to where you ran the command, so you can copy the
path straight from it. Each line is one event, in the order it happened.

| Event | What it records |
| --- | --- |
| `run:start` | The run began. It carries the run id and record path when the run has them. |
| `run:end` | The run ended. It carries the same outcome and token usage that `run()` returns. |

A run appends `run:start` when it begins and `run:end` only if it finishes.
So a record still being written has a start and no end, and so does one
whose run was killed. A resumed record keeps the earlier start as well.

## One event per step, appended as it happens

Each event is appended to the file the moment it happens: a node started,
an engine call returned, a review sent work back, a gate paused for an
answer. An event that has landed is never rewritten, so a later step can't
change what an earlier one recorded.

## Why events and artifacts are the whole record

The event file holds every decision and outcome, and each engine call with
its usage. It leaves out the model's streamed text. In the supervised
runner's store, the run's state is rebuilt from its events, and anything too
large for an event sits in the artifact directory. The event carries a small
reference to it, with its digest.

## Which layer restarts a killed run

The runner package's supervised run does. It starts the run in a bounded
worker. When the worker dies, it starts another against the run's own store.
The new worker reads that store and carries on. Steps that finished are
never repeated. A step that was mid-flight when the worker died runs again
only if its binding declares it safe to retry; otherwise the run pauses and
asks a person to reconcile it before it continues, so uncertain work is
never repeated silently.

The file shown above is the record of a plain `run()`. A plain run opens a
fresh record each time it starts. With `resume: true`, it reads the record
at `recordTo` first. For a job built with `workflow()`:

- **A stage that finished** is skipped.
- **A stage that failed** runs again.
- **A gate still waiting for a person** isn't asked twice, as long as the
  resumed run reads the same store of pending questions. A run given a fresh
  in-memory client has nothing to read, so it asks again.
  [Callback gates](/reviewing/callback-gates) covers how a run waits for the
  answer.
- **A stage that was mid-flight** when the process died runs again only when
  it carries `retrySafe: true`. Otherwise the run pauses and asks a person to
  reconcile it. If the person says it didn't finish, the stage runs in the
  same resumed run. If it did finish, the stage isn't repeated.

The record applies only to the same workflow name, workspace, brief and
stage list, and to the seat each role names. Change the brief, the model
behind a role, or the question a person role asks, and the run starts again.
Any other job given `resume: true` appends to the record and runs again.
`resume: true` is how a workflow carries on when you start it yourself or a
schedule starts it for you.

## Why there is nothing to install beside it

The record is plain files the runtime already writes. Reading them and
restarting from them needs no database and no server.
